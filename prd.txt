# Portfolio Website

## Product Requirements Document

**Product:** Personal Developer / Engineer Portfolio
**Status:** Existing Project / Direction & Refactor Phase
**Primary Purpose:** Professional portfolio and project showcase
**Primary Audience:** Recruiters, hiring managers, technical leads, collaborators, and potential clients

---

# 1. Product Overview

The Portfolio Website is a personal professional site designed to present my technical background, projects, skills, and experience in a clear and highly visual format.

The portfolio should emphasize practical work across multiple technical disciplines rather than presenting me exclusively as a traditional software developer.

The primary project categories are:

* Embedded Systems / IoT
* Artificial Intelligence / Machine Learning
* Web Development
* Mobile Development
* Software Development

The website must communicate what I work on, what technologies I have used, and what I personally contributed to each project without requiring visitors to read large amounts of text.

The core principle of the portfolio is:

> **Show the work. Explain it quickly. Provide details only when they matter.**

---

# 2. Problem Statement

The current portfolio has an established visual design but lacks a clear content hierarchy and overall product direction.

The website needs to answer the following questions for a visitor within a short amount of time:

1. Who am I?
2. What kind of technical work do I do?
3. What technologies do I know or have experience using?
4. What projects have I actually built?
5. What did I personally contribute to those projects?
6. How can someone contact or learn more about me?

The portfolio should avoid becoming a large personal biography or an overly technical project archive.

Instead, it should act as a concise professional showcase.

---

# 3. Product Goals

## Primary Goals

### G1. Present a clear professional identity

Visitors should quickly understand that my experience spans hardware, embedded systems, IoT, AI/ML experimentation, and software development.

### G2. Make projects the central focus

Projects should serve as the strongest evidence of technical ability.

### G3. Keep information concise

Descriptions should be brief, readable, and useful.

The visitor should not encounter unnecessary walls of text.

### G4. Make technical experience easy to scan

Technologies, project categories, responsibilities, and outcomes should be visually identifiable without reading the entire project description.

### G5. Support job applications

The portfolio should function as a companion to a résumé and give recruiters more context about projects that cannot reasonably fit inside a résumé.

### G6. Remain maintainable

Adding, editing, removing, or reordering projects should require minimal changes to the application's UI code.

---

# 4. Non-Goals

The portfolio is **not intended to be:**

* A full technical documentation website
* A personal social media platform
* A long-form technical blog
* A GitHub replacement
* A complete résumé displayed as a webpage
* A tutorial platform
* A project-management application
* An exhaustive list of every experiment or school activity

Only projects that meaningfully demonstrate skills or experience should be included.

---

# 20. Visual Design Direction

The existing visual identity will remain based on **Bauhaus / Constructivist Modernism**.

The UI should feel:

* Geometric
* Technical
* Bold
* Architectural
* Functional
* Deliberate

The design should use geometric elements as part of the composition while maintaining clarity and usability.

# 22. Interaction Design

Interactions should feel mechanical and responsive.

Recommended behavior:

### Buttons

On click:

* Slight downward/right translation
* Shadow disappears momentarily

### Project Cards

On hover:

* Small upward movement
* Optional visual accent

### Images

Optional treatment:

* Grayscale normally
* Full color on hover

### Filters

Category selection should transition quickly and clearly indicate the active category.

Animations should remain approximately:

**200–300ms**

Avoid long, floating, or overly organic animation.

---

# 23. Responsive Requirements

The portfolio must support:

### Mobile

Below 640px

### Tablet

640px–1024px

### Desktop

Above 1024px

The design must remain usable rather than simply shrinking the desktop layout.

Expected behavior:

* Single-column project layouts on small screens
* Multi-column project grids on larger screens
* Responsive typography
* Mobile navigation
* Reduced decorative geometry where necessary

Decorative elements must never interfere with readability or interaction.

---

# 24. Accessibility Requirements

The site should:

* Maintain readable color contrast
* Support keyboard navigation
* Provide visible focus states
* Include alt text for meaningful images
* Use semantic HTML
* Avoid requiring hover for essential information
* Respect reduced-motion preferences where possible

Visual experimentation must not reduce usability.

---

# 25. Performance Requirements

The portfolio should prioritize fast loading.

Requirements:

* Compress project images
* Lazy-load non-critical media
* Avoid unnecessarily large dependencies
* Avoid excessive animation libraries
* Minimize JavaScript required for purely visual effects
* Optimize assets for web delivery

Primary content should remain usable before all decorative elements finish loading.

---

# 26. Content Principles

All portfolio copy should follow the following rules.

### Be Direct

Instead of:

> An innovative and revolutionary IoT-powered solution designed to transform how modern retail environments...

Use:

> IoT shelf system that monitors product stock using load cells and connected embedded hardware.

### Explain Results Before Implementation

Visitors should first understand **what the project does**.

Technical implementation comes afterward.

### Avoid Buzzwords

Avoid unnecessary phrases such as:

* Cutting-edge
* Revolutionary
* Game-changing
* World-class
* Next-generation

unless objectively justified.

### Prioritize Contributions

For collaborative projects, clearly distinguish personal work from the work of the team.

# 31. Final Product Principle

The portfolio should not attempt to prove technical ability by overwhelming visitors with information.

The project itself should demonstrate quality through:

**clarity + organization + engineering + visual identity.**

Every section should answer a specific question.

> **What is it?**

> **What did I use to build it?**

Anything that does not help answer those questions should have a strong reason for being on the site.


# Project Asset & Folder Management

## Purpose

Project content should be easy to maintain without requiring changes to UI components every time a new screenshot or photograph is added.

Each project must therefore have its own dedicated folder containing the project's visual assets.

The website should automatically use supported images found inside that project's folder to build its image carousel/gallery.

The intended workflow should be:

> **Add image to project folder → site includes it in the project's gallery.**

Adding project media should not require manually modifying the carousel component.

---

## Project Folder Structure

Each project should have a unique folder using the same identifier as the project's `id` or `slug`.

Recommended structure:

```text
projects/
│
├── smart-shelf/
│   ├── cover.webp
│   ├── gallery/
│   │   ├── 01-shelf.webp
│   │   ├── 02-electronics.webp
│   │   ├── 03-dashboard.webp
│   │   └── 04-testing.webp
│
├── ai-group-detection/
│   ├── cover.webp
│   ├── gallery/
│   │   ├── 01-demo.webp
│   │   ├── 02-detection.webp
│   │   └── 03-interface.webp
│
└── mobile-job-portal/
    ├── cover.webp
    └── gallery/
        ├── 01-home.webp
        ├── 02-jobs.webp
        └── 03-profile.webp
```

The folder name should match the project's unique identifier.

Example:

```text
Project ID:
smart-shelf

Asset Folder:
projects/smart-shelf/
```

This provides a predictable relationship between project data and project media.

---

## Cover Image

Every project may contain a designated:

```text
cover.webp
```

The cover image should be used for:

* Project cards
* Featured project previews
* Social/link previews where applicable
* Initial project gallery image

If no dedicated cover image exists, the system may use the first available gallery image.

If no project images exist, the card should use the site's standard project placeholder design.

A missing image must never break the project card.

---

## Gallery Folder

Additional project media should be stored inside:

```text
gallery/
```

Example:

```text
projects/smart-shelf/gallery/
```

The website should automatically discover supported media inside this directory and display it in the project carousel.

Adding:

```text
05-rfid-testing.webp
```

to the folder should cause the image to appear in the Smart Shelf gallery without requiring modifications to the project component.

---

## Supported Image Formats

The gallery should support common optimized web formats:

* `.webp`
* `.avif`
* `.jpg`
* `.jpeg`
* `.png`

Preferred formats:

1. WebP
2. AVIF
3. JPEG/PNG when required

Large source photographs should be optimized before production deployment where practical.

---

## Gallery Ordering

Gallery images should be displayed according to filename order.

Recommended convention:

```text
01-overview.webp
02-hardware.webp
03-dashboard.webp
04-testing.webp
05-final-prototype.webp
```

This makes carousel order controllable directly through filenames.

Alphabetical filenames without numeric prefixes are permitted, but numbered filenames are recommended.

---

## Carousel Requirements

If a project contains multiple gallery images, its project detail view should display them using a carousel.

The carousel should provide:

* Previous image control
* Next image control
* Current image indicator
* Image count
* Keyboard navigation where appropriate
* Swipe support on touch devices
* Responsive image sizing
* Accessible image descriptions when provided

Example:

```text
←    [ PROJECT IMAGE ]    →

          2 / 6
```

Optional enhancements:

* Thumbnail navigation
* Full-screen image viewer
* Click-to-enlarge
* Image captions

The carousel should remain visually consistent with the Bauhaus design system.

Controls should use the same:

* Thick borders
* Hard shadows
* Primary colors
* Geometric forms
* Mechanical interaction behavior

as the rest of the interface.

---

## Project Card Behavior

Project cards should normally display only the project's cover image.

The full gallery should not load eagerly for every project card on the main portfolio page.

This prevents a portfolio containing many project photographs from unnecessarily loading every image when the visitor first enters the site.

The complete gallery should be loaded when the visitor opens the relevant project.

---

## Updated Project Data Model

Projects should remain structured data rather than individually hard-coded UI components.

The project model should support:

```text
id
slug
title
category
shortDescription
description
technologies
contributions
assetFolder
year
featured
githubUrl
demoUrl
documentationUrl
status
```

Example:

```text
id: "smart-shelf"
slug: "smart-shelf"
assetFolder: "smart-shelf"
```

The application should derive:

```text
cover image
gallery images
```

from the project's asset folder whenever possible.

This means the project data should **not normally require this:**

```text
images:
  - "/projects/smart-shelf/01.webp"
  - "/projects/smart-shelf/02.webp"
  - "/projects/smart-shelf/03.webp"
  - "/projects/smart-shelf/04.webp"
```

Instead:

```text
assetFolder: "smart-shelf"
```

should be sufficient.

The application is then responsible for discovering the media belonging to that project.

---

## Recommended Content Architecture

A project should conceptually consist of two parts:

```text
PROJECT DATA
+
PROJECT ASSETS
```

Example:

```text
projectData/
└── smart-shelf.ts

projects/
└── smart-shelf/
    ├── cover.webp
    └── gallery/
        ├── 01-overview.webp
        ├── 02-electronics.webp
        └── 03-dashboard.webp
```

The project data contains information such as:

* Name
* Description
* Category
* Technologies
* Contributions
* Links

The project asset folder contains:

* Cover image
* Screenshots
* Photographs
* Diagrams
* UI previews

This separation keeps project information organized while making media management simple.

---

## Developer Experience Requirement

Adding media to an existing project should ideally require only:

1. Open the project's folder.
2. Copy the new image into `gallery/`.
3. Give it the desired numeric filename.
4. Rebuild/redeploy the portfolio.

No carousel source code should need modification.

No React/UI component should need modification.

No manual image import should be required where the application's build system supports automatic asset discovery.

---

## Adding a New Project

The intended workflow for creating a new project should be:

```text
1. Add project metadata.
2. Create matching project folder.
3. Add cover image.
4. Add gallery images.
5. Run/build site.
```

Example:

```text
Project:

id: "drone-system"
```

Create:

```text
projects/
└── drone-system/
    ├── cover.webp
    └── gallery/
        ├── 01-assembly.webp
        ├── 02-flight.webp
        └── 03-final.webp
```

The portfolio should then associate those assets with the `drone-system` project.

---

## Error Handling

The application must handle incomplete asset folders gracefully.

### No project folder

Display the site's default project placeholder.

### Folder exists but has no cover

Use the first gallery image where possible.

### Folder contains no gallery images

Display the cover image without carousel controls.

### One gallery image

Display the image normally without unnecessary previous/next controls.

### Multiple gallery images

Enable the carousel.

A missing or incorrectly named image must not cause the Projects section or portfolio application to crash.

---

## Performance Requirements

Project galleries should use:

* Lazy loading
* Responsive image dimensions
* Optimized image formats
* Appropriate compression
* Deferred loading for galleries that have not been opened

The project listing should prioritize loading project cover images rather than complete galleries.

---

## Final Asset Management Principle

The portfolio's project system should be **content-driven rather than component-driven**.

Adding another photo should be a file-management task, not a programming task.

Adding another project should primarily involve:

> **Project metadata + project folder**

rather than:

> **New component + new imports + new carousel configuration + new route logic.**

The system should be designed so that maintaining the portfolio remains simple even after dozens of projects have been added.
